# WP5: automatic alert scoring

The scheduled task ("StreetEasy alert check") already ran hourly to find
new listings via Gmail. WP5 makes it also score each new listing before
messaging you, so the summary you see is "here's a real pick, worth a
look" rather than just a bare address.

## Why this can't just call `etl/match_listings.py`

The scheduled task runs as a **fresh cloud session every time it fires**
-- it has no access to your local machine, your local `registry.db`, or
`data/processed/registry.csv` (which is large and deliberately never
pushed to the project -- see `claude/status.md`). It also can't run raw
`curl`/`urllib` calls the way your local machine can; the sandbox's shell
network access is locked to package registries only.

So WP5 uses what the scheduled task *does* have:
- **The WebFetch tool** (not a shell call) to hit NYC's free GeoSearch
  geocoder directly -- WebFetch goes through Claude's own infrastructure,
  not the sandbox's restricted shell egress.
- **Two small project docs**, purpose-built to fit in a scheduled task's
  context cheaply:
  - `code/park_anchors.json` -- one representative centroid point per
    anchor park (12 entries, ~1KB). Built from `geo/load_parks.py`'s
    already-vetted `PLACEHOLDER_PARK_POINTS`.
  - `data/registry-lookup.json` -- a compact `{bbl: {stabilization_
    confidence, building_safety_tier}}` map (currently ~19.5k BBLs,
    ~1.5MB), stripped of every other registry column. Generated by the
    new `etl/export_registry_lookup.py` script.

## The trade-off: estimate now, precise later

WP5's score (`match_score_estimate`) is deliberately a **coarser, faster**
version of `etl/match_listings.py`'s real score:

| | WP5 (scheduled, automatic) | `match_listings.py` (local, on-demand) |
|---|---|---|
| Park distance | straight-line to one centroid per park, x1.3 circuity | real OSRM/ORS routing to full park boundary |
| Runs | every hour, automatically, on new listings only | manually, whenever you want |
| Registry data | compact lookup (2 fields), can go stale | full registry.csv, always current if freshly rebuilt |

The alert message always says these are estimates and points you at
`etl/match_listings.py` for the authoritative number on anything that
looks promising.

## Keeping `data/registry-lookup.json` fresh

The registry-lookup doc goes stale the moment you re-run
`etl/build_registry.py` locally (new HPD/rentstab data, etc.) -- it does
NOT update itself. Refresh it with:

```bash
python3 etl/export_registry_lookup.py
```

Then attach the resulting `data/processed/registry_lookup.json` to a
Claude chat and ask Claude to push it to the project as
`data/registry-lookup.json` (it'll `project_write` it in place). There's
no way to automate this last step from your machine directly -- the
project only accepts writes from inside a Claude session.

`code/park_anchors.json` only needs refreshing if the anchor park list
itself changes (new target neighborhood, etc.) -- not on every registry
rebuild.

## What you'll see

When a run finds new listings, the task's reply now includes, per
listing: address, neighborhood, price, beds, URL, `match_score_estimate`
(0-100), `stabilization_confidence`, `building_safety_tier`, and the
estimated nearest park + walk time. A listing whose address couldn't be
geocoded still gets reported (with a note), not silently dropped.

## Status: live, not yet exercised on a real listing

As of this write-up, no real StreetEasy alert email has arrived yet
(`state/email-alert-state.json` shows every run coming back empty since
the saved search was set up 2026-09-19), so this scoring path hasn't
actually run against real data. The underlying pieces (`etl/match_
listings.py`'s identical scoring formula, `geo/geocode.py`'s GeoSearch
integration) were unit-tested with mocked data -- see `docs/WP4-
matching.md`. The scheduled task's own WebFetch-based geocoding is
untested until a real alert triggers it.
