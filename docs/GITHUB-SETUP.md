# GitHub setup

This covers two separate things:

1. **Put the repo on GitHub** — version control, backup, and a prerequisite
   for #2. Do this regardless.
2. **A free scheduled GitHub Actions workflow** to re-run the data-pulling
   ETL scripts (`etl/build_registry.py` and friends) on a schedule, instead
   of only running them by hand on your laptop.

**What this does NOT cover**: the hourly Gmail-alert polling (WP3b) stays
on Claude's own scheduled task — moving that to GitHub Actions would mean
setting up Gmail API OAuth credentials as a GitHub secret, which is real
extra work for something that's already running for $0 today. Only move
it if the Claude scheduled task itself stops working for you.

## 1. Put the repo on GitHub

From your local `rent-tool` folder (`/Users/jake.smith/Downloads/rent-tool`):

```bash
cd /Users/jake.smith/Downloads/rent-tool
git init
git branch -m main
```

Add a `.gitignore` so you don't commit large/regenerable data or (if you
ever add one) API keys:

```bash
cat > .gitignore << 'EOF'
# Regenerated by the ETL scripts -- don't commit, they're large and
# derived, not source.
data/raw/*.csv
data/raw/*.json
data/interim/*.db
data/interim/*.csv
data/processed/*.csv

# Real DHCR PDF / other large manual downloads
data/raw/*.pdf

# Never commit secrets
.env
*.key

# Python
__pycache__/
*.pyc
EOF
```

Keep `data/external/dhcr_historical_mirror/` and `fixtures/` — those are
small, checked-in reference data the scripts expect to find (the mirror
was git-cloned from a public repo already, and the fixtures are tiny
synthetic/sample files used for tests, not real listings data).

Then create the GitHub repo itself:

1. Go to [github.com/new](https://github.com/new).
2. Name it (e.g. `rent-tool`). **Public**, not private — this is what
   gives you unlimited free GitHub Actions minutes (see
   `claude/hosting-research.md` for why private-repo minutes are capped at
   2,000/month on the free tier). A personal side project with no secrets
   in it is a reasonable thing to make public; double-check nothing
   sensitive (your email, real addresses you're tracking) ends up
   committed if that matters to you — the `.gitignore` above keeps the
   generated data files out, but do a `git status` before your first
   commit and eyeball it.
3. Don't initialize with a README/gitignore/license on GitHub's side (you
   already have files locally) — leave it empty.
4. Push:

```bash
git add .
git status   # sanity-check what's about to be committed
git commit -m "Initial commit"
git remote add origin https://github.com/<your-username>/rent-tool.git
git push -u origin main
```

If `git push` asks for a password, GitHub no longer accepts your account
password there — use a [personal access token](https://github.com/settings/tokens)
(classic, `repo` scope) as the password instead, or set up the GitHub CLI
(`gh auth login`) and use `gh repo create` to do steps 2-4 in one go.

## 2. A scheduled GitHub Actions workflow for the ETL scripts

This re-runs `etl/load_rentstab.py` + `etl/load_building_issues.py` +
`etl/build_registry.py` on a schedule, so the registry stays current
without you remembering to run it by hand — useful once you've done the
manual data fetches (the real DHCR PDF, PLUTO, nycdb rentstab CSVs, HPD
violations CSV) at least once and want the scoring/joining logic to
re-run periodically as those source files change.

Create `.github/workflows/etl.yml`:

```yaml
name: Weekly ETL rebuild

on:
  schedule:
    # Every Monday 13:00 UTC (~8am Eastern). Cron is in UTC always.
    - cron: '0 13 * * 1'
  workflow_dispatch: {}   # lets you also trigger it manually from the Actions tab

jobs:
  rebuild-registry:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: '3.11'

      - name: Install dependencies
        run: pip install -r requirements.txt

      - name: Run ETL pipeline
        run: |
          python3 etl/load_rentstab.py
          python3 etl/load_building_issues.py
          python3 etl/build_registry.py

      - name: Commit updated registry
        run: |
          git config user.name "github-actions[bot]"
          git config user.email "github-actions[bot]@users.noreply.github.com"
          git add data/processed/registry.csv
          git diff --staged --quiet || git commit -m "Auto-update registry ($(date -u +%Y-%m-%d))"
          git push
```

Notes:
- This assumes the manual-fetch source files (`data/raw/*.csv`,
  `data/raw/*.pdf`) are ALREADY present in the repo when this runs — the
  `.gitignore` above excludes them, so if you want this workflow to have
  real data to work with, either commit those specific files anyway (they
  don't change often) or adjust the `.gitignore` to allow them. Otherwise
  this workflow will just keep re-running against empty/fallback data,
  same as this sandbox has been doing.
- **The 60-day auto-disable**: a scheduled workflow on a repo with zero
  commits for 60 days gets automatically disabled by GitHub. The commit
  step above ("Commit updated registry") itself counts as repo activity
  each time it runs, so as long as this workflow keeps succeeding on
  schedule, it keeps itself alive — no separate keepalive step needed
  *for this specific workflow*, since it always commits when it runs
  (even a no-op run still makes a commit attempt). If you later add a
  workflow that never commits anything (e.g. one that just reads and
  reports), add a trivial keepalive step to it separately.
- Cron scheduling on GitHub Actions can drift 5-15+ minutes under load —
  fine for a weekly rebuild, don't rely on it for anything time-sensitive.
- If you later wire in `ORS_API_KEY` (from `geo/distance.py`'s
  OpenRouteService backend) into a workflow, add it as a **repository
  secret** (Settings → Secrets and variables → Actions → New repository
  secret) and reference it as `${{ secrets.ORS_API_KEY }}` in the
  workflow's `env:` — never commit an API key directly into a workflow
  file or the repo.

## Optional: a static results page via GitHub Pages

If you later want a simple webpage to check your matched listings from
your phone instead of asking Claude, per `claude/hosting-research.md`'s
recommendation: add a step to the workflow above that exports
`data/processed/registry.csv` (or `data/streeteasy-matches.json`) to a
small static HTML page, commit it to a `gh-pages` branch or a `/docs`
folder, and turn on GitHub Pages for the repo (Settings → Pages → Source:
the branch/folder you used). This is a separate follow-up, not something
set up yet — flagging it here since it's the natural next step if you
want a browsable page rather than files sent through Claude.
